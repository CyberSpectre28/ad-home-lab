# Ticket 004: "Group Policy and network shares stopped working"

| Field | Value |
|---|---|
| User | Devon Clarke (`dclarke`) |
| Device | CLIENT01 |
| Priority | High (no policy, no domain resources) |
| Status | Resolved |

## Setup (lab only)
To simulate a common real-world mistake, CLIENT01's DNS server was changed from the DC to Google's public DNS (8.8.8.8) with `Set-DnsClientServerAddress`.

## Symptoms
- `gpupdate /force` failed: "Windows could not resolve the computer name" and "could not resolve the user name."
- `dir \\lab.local\SYSVOL` failed: "Cannot find path because it does not exist."

## Diagnosis (CLIENT01)
1. `Get-DnsClientServerAddress` showed the lab adapter using **8.8.8.8** instead of DC01 (192.168.56.10).
2. `Test-NetConnection 192.168.56.10 -Port 445` succeeded, so the network path to DC01 was fine.
3. `nslookup lab.local` failed against 8.8.8.8 ("No response from server").
4. `nslookup lab.local 192.168.56.10` succeeded, proving DC01's DNS was healthy.

Conclusion: the client was asking the wrong DNS server. Public DNS has no record of the internal `lab.local` domain.

## Resolution
- In an elevated PowerShell (a standard user can't change network settings): `Set-DnsClientServerAddress -InterfaceAlias "Ethernet" -ResetServerAddresses`, which returns the adapter to the DNS server handed out by DHCP (DC01).
- `ipconfig /flushdns` to clear cached failures.

## Verification
`nslookup lab.local` answered from 192.168.56.10, `gpupdate /force` completed for both computer and user policy, and `\\lab.local\SYSVOL` opened.

## Lessons learned
- **Domain-joined computers must use the domain controller for DNS.** Active Directory finds DCs, Kerberos and Group Policy through DNS records. If a client needs internet name resolution, the DC's DNS server should forward those queries upstream, not the client.
- **Test by IP, then by name.** A working connection by IP plus a failed lookup by name points straight at DNS.
- **DNS failures can block admin sign-ins too.** Elevating with a domain account requires reaching a DC, so a working local admin account (managed by LAPS in production) is a useful fallback.
- The "DNS request timed out / Server: UnKnown" line in `nslookup` comes from the missing reverse lookup zone, not from this incident. Adding a reverse zone is listed as a future improvement.
